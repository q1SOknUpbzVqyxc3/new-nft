# Обязательные инструкции для AI-агента

## 1. Статус документа

Правила этого файла обязательны для всей дальнейшей разработки проекта.

Перед любыми изменениями агент обязан прочитать:

- `AGENT.md`;
- `DESIGN.md`;
- `ARCHITECTURE.md`;
- `TODO.md`;
- `README.md`, если он существует;
- конфигурацию проекта;
- более локальные инструкции в рабочих каталогах, если они появятся.

При конфликте правил приоритет имеют:

1. Прямое актуальное указание пользователя в текущем диалоге.
2. Более локальные инструкции для изменяемого каталога.
3. Этот файл.
4. `ARCHITECTURE.md` и `DESIGN.md`.
5. Существующие соглашения проекта.

## 2. Уровень разработки

- Работать как Senior / Staff Fullstack Developer.
- Любой код должен быть production-ready, типобезопасным, тестируемым, безопасным и поддерживаемым.
- Не писать временные решения, костыли, заглушки и demo-only реализацию без прямого запроса пользователя.
- Не подменять реальную интеграцию фиктивными данными и не выдавать mock за работающую функциональность.
- Если полноценная реализация заблокирована контрактом, доступом или продуктовым решением, явно сообщить об этом и не имитировать успех.
- Если существующий код плохого качества, не копировать его подход автоматически. Выбирать более правильное современное решение, сохраняя совместимость там, где она требуется.

## 3. Обязательный аудит перед реализацией

Перед началом новой крупной реализации:

1. Изучить весь существующий проект и связанные конфигурации.
2. Проверить Git-состояние, текущую ветку и существующий diff.
3. Определить текущий стек и структуру приложения.
4. Найти архитектурные и security-проблемы.
5. Найти дублирование и устаревшие зависимости.
6. Определить, какие части можно безопасно сохранить.
7. Сверить решение с `DESIGN.md` и `ARCHITECTURE.md`.
8. Обновить технический план в `TODO.md`, если фактическое состояние изменилось.

Не начинать массовую реализацию, пока аудит не завершён и выбранная архитектура не проверена на технический долг, безопасность и сопровождение.

## 4. Работа с существующим проектом

- Перед изменением файла прочитать его полностью или достаточно большой связанный контекст.
- Перед созданием компонента проверить, нет ли уже аналогичного.
- Перед созданием util, helper, hook или service проверить существующие реализации.
- Не дублировать функциональность.
- Не переписывать большой участок без объективной необходимости.
- Не изменять файлы вне области текущей задачи.
- Не удалять и не откатывать чужие изменения.
- Сохранять backward compatibility, если пользователь прямо не запросил breaking change.
- Не форматировать весь файл ради локальной правки.
- Сохранять кодировку, line endings и формат данных, если задача не требует их изменения.
- Не редактировать вручную сгенерированные файлы и lockfile.

## 5. Качество кода

- Не добавлять комментарии в код без крайней необходимости.
- Код должен быть понятен за счёт хороших названий, правильной архитектуры, небольших функций, строгой типизации и чёткого разделения ответственности.
- Комментарий допустим только для неочевидного внешнего ограничения, требования протокола, лицензии, генератора или публичной API-документации.
- Не оставлять TODO, FIXME, `console.log`, debug-код, закомментированный старый код, неиспользуемые импорты и мёртвый код.
- Не использовать `any`, если этого можно избежать.
- Не использовать небезопасные cast и non-null assertion без обоснованной границы с внешними данными.
- Не отключать ESLint, TypeScript и другие проверки ради успешной сборки.
- Не подавлять правило линтера без доказанной необходимости и узкой области действия.
- Предпочитать небольшие функции, ранний возврат, явные контракты и композицию.
- Не создавать абстракцию без подтверждённого повторного использования или устойчивой границы ответственности.
- Не оставлять временные файлы, бесхозные feature flags и скрытое поведение.

## 6. Архитектура

- Перед разработкой определить и зафиксировать архитектуру в `ARCHITECTURE.md`.
- Разделять UI, бизнес-логику, API, работу с данными, состояние, утилиты, типы и конфигурацию.
- Не создавать огромные компоненты.
- Компонент с несколькими обязанностями или чрезмерным размером разбивать по устойчивым границам.
- Бизнес-логика не должна зависеть от UI и конкретного транспорта.
- API-контракты должны быть типизированы и централизованы.
- Не смешивать server state, глобальное client state и локальное состояние формы.
- Публичный API модуля должен быть минимальным.
- Циклические зависимости запрещены.
- Следовать SOLID там, где он полезен, DRY без фанатизма, KISS, Separation of Concerns и Composition over inheritance.
- Избегать чрезмерной абстракции.
- Не создавать wrapper, helper или service только ради дополнительного слоя.

## 7. TypeScript

- Использовать strict mode со всеми разумными строгими проверками проекта.
- Типы должны описывать реальные domain entities и состояния.
- Запрещены бессмысленные конструкции вроде `type Data = any`.
- Не создавать один огромный универсальный интерфейс на весь проект.
- Использовать discriminated unions для конечных состояний и результатов, где это улучшает безопасность.
- Предпочитать inference там, где тип очевиден.
- Валидировать внешние данные во время выполнения, даже если транспорт предоставляет TypeScript-типы.
- Не считать type assertion валидацией данных.

## 8. Naming

- Названия должны точно описывать назначение и соответствовать единому naming convention проекта.
- Запрещены бессмысленные имена: `data2`, `temp`, `test123`, `stuff`, `helper2`, `finalData`, `newComponent` и их аналоги.
- Boolean-значения называть так, чтобы состояние читалось однозначно.
- Функции-действия называть глаголами, domain entities — предметными терминами.
- Не использовать сокращения, если они не являются общеупотребимыми терминами домена.

## 9. Frontend

- Интерфейс должен строго соответствовать `DESIGN.md`.
- OpenSea и Magic Eden используются только как референсы UX, структуры и визуального уровня. Копирование 1:1 запрещено.
- Проект должен иметь собственный визуальный язык.
- Повторяющиеся цвета, spacing, radius, shadows, typography, breakpoints и animation timings задаются через design tokens.
- Не использовать случайные значения вроде `margin: 17px`, если они не обоснованы дизайном.
- Создавать переиспользуемый компонент только при реальном повторяющемся паттерне.
- Не скрывать критические действия только за hover.
- Не использовать misleading UI и неподтверждённые финансовые показатели.
- Не сообщать об успехе операции до подтверждения соответствующим источником данных.

Интерфейс должен быть полностью адаптивным для mobile, tablet, desktop и wide desktop. Обязательные контрольные ширины:

- 320 px;
- 375 px;
- 768 px;
- 1024 px;
- 1440 px;
- 1920 px.

Нельзя допускать непреднамеренный horizontal overflow, layout shift, перекрытие контента и элементы управления меньше доступного touch target.

Для компонентов и экранов обязательны применимые состояния:

- loading;
- skeleton;
- empty;
- error;
- disabled;
- hover;
- active;
- focus;
- success.

Все интерактивные элементы должны давать понятный feedback. Анимации должны быть быстрыми, аккуратными и не перегружать интерфейс. Обязательно учитывать `prefers-reduced-motion`.

## 10. UX

- Пользователь должен быстро понимать, где находится, что может сделать, что кликабельно и где основное действие.
- Не использовать лишние модальные окна.
- Не прятать важные действия без причины.
- Критические и необратимые действия должны иметь подтверждение с точным описанием результата.
- Не использовать dark patterns, ложный urgency, скрытые комиссии и misleading UI.
- Ошибка должна объяснять проблему и предлагать следующее полезное действие.
- Empty state должен объяснять причину и содержать релевантный путь продолжения.

## 11. Accessibility

- Минимальная цель — WCAG 2.1 AA; по возможности соблюдать более актуальный WCAG 2.2 AA.
- Использовать semantic HTML.
- Обеспечивать полную keyboard navigation.
- Каждый интерактивный элемент должен иметь видимый focus-state.
- Использовать ARIA только там, где semantic HTML недостаточно.
- Проверять контраст текста, контролов и focus indicator.
- Смысловые изображения должны иметь корректный `alt`, декоративные — пустой `alt`.
- Modal, dialog, menu, tabs, combobox и drawer должны корректно управлять focus и следовать WAI-ARIA patterns.
- Ошибки форм должны быть программно связаны с полями.
- Статусы асинхронных операций должны корректно объявляться assistive technologies.

## 12. Производительность

- Контролировать bundle size, unnecessary rerenders, layout shifts, oversized images, лишние API-запросы и waterfall-загрузки.
- Использовать lazy loading только там, где он улучшает загрузку и не ухудшает основной сценарий.
- Оптимизировать изображения, задавать их размеры и использовать responsive sources.
- Не применять memoization без измеренной или очевидной необходимости.
- Не импортировать большую библиотеку ради одной простой функции.
- Не создавать N+1 запросы, бесконтрольный polling и неограниченные списки.
- Кэширование должно иметь понятную стратегию invalidation.
- Большие коллекции должны использовать pagination, а виртуализацию — только после подтверждения необходимости.
- Цели frontend на 75-м перцентиле: LCP до 2.5 s, INP до 200 ms, CLS до 0.1.
- Производительность подтверждается измерениями, а не предположениями.

## 13. API и данные

- Использовать единый подход к API-запросам.
- Не вызывать API хаотично непосредственно из UI-компонентов.
- Отделять транспорт, runtime-валидацию, преобразование DTO и domain model.
- Обрабатывать loading, error, retry, timeout, empty response и invalid response.
- Retry разрешён только для безопасных операций либо при обеспеченной идемпотентности.
- Внешние данные всегда считать недоверенными и валидировать на входной границе.
- Не доверять client-side validation как единственной защите.
- Не доверять цене, балансу, роли, комиссии и итоговой сумме, пришедшим только от клиента.
- Изменяющие состояние запросы должны учитывать авторизацию, идемпотентность и повторную отправку.
- Контракты request, response и ошибок должны быть явными и версионируемыми при необходимости.

## 14. Backend

- Авторизацию проверять на сервере для каждого защищённого действия.
- Не путать authentication и authorization.
- Денежные и blockchain-операции должны быть идемпотентными и аудируемыми.
- Для внешних сервисов использовать timeout, ограниченные retries, circuit-breaking или контролируемую деградацию по необходимости.
- Изменение схемы данных должно иметь безопасную миграцию и оценку обратной совместимости.
- Логи должны быть структурированными и не содержать секреты или избыточные персональные данные.
- Фоновые задачи должны иметь retry policy, dead-letter стратегию и защиту от повторной обработки, если это применимо.

## 15. Web3

- Никогда не запрашивать seed phrase или private key пользователя.
- Все blockchain actions должны явно показывать, что произойдёт.
- Перед транзакцией показывать действие, сеть, сумму, asset и fees, если они доступны.
- Корректно обрабатывать user rejection, wrong network, disconnected wallet, pending transaction, failed transaction и confirmed transaction.
- Не считать wallet address доказательством авторизации для authenticated session без проверки подписанного challenge.
- Nonce должен быть одноразовым, иметь срок жизни и проверяться сервером.
- Не доверять NFT metadata только потому, что она получена из blockchain или indexer.
- Любой HTML, SVG, URI и metadata content считать потенциально вредоносным.
- Не рендерить непроверенный active content в origin приложения.
- Проверять chain ID, contract address, token ID, decimals и recipient на доверенной границе.
- Не обещать подтверждение транзакции до достаточного числа подтверждений или финальности выбранной сети.

## 16. Безопасность

- Никогда не хардкодить API keys, private keys, access tokens, passwords и secrets.
- Использовать environment variables или утверждённый secret manager.
- Не добавлять `.env` с секретами в Git.
- Поддерживать `.env.example` только с безопасными placeholders и описанными обязательными переменными.
- Применять least privilege, deny by default и defense in depth.
- Учитывать XSS, CSRF, injection, SSRF, path traversal, unsafe redirects, insecure storage, exposed secrets, broken authorization и IDOR.
- Не использовать `dangerouslySetInnerHTML` без крайней необходимости, строгой sanitization и тестов.
- Не хранить чувствительные токены в `localStorage`, если доступен более безопасный механизм.
- Cookies сессии должны использовать подходящие `HttpOnly`, `Secure` и `SameSite` параметры.
- Не логировать токены, cookies, seed phrases, private keys и чувствительные параметры транзакций.
- Любое разрушительное действие должно иметь точную цель, проверку полномочий и явное подтверждение.

## 17. Dependency policy

- Использовать последние stable версии библиотек, фреймворков, runtime и инструментов, совместимые между собой.
- Не использовать alpha, beta, rc, canary и nightly без прямого разрешения пользователя.
- Перед установкой зависимости проверить, действительно ли она нужна.
- Если функциональность надёжно и просто реализуется нативными средствами, не добавлять dependency.
- Не заменять рабочую библиотеку только из-за существования более новой альтернативы без объективной пользы.
- Перед major-обновлением проверить breaking changes, migration guide, совместимость, лицензию, поддержку и security advisories.
- Lockfile обязателен и изменяется только package manager проекта.
- Не менять package manager без прямого указания пользователя.
- После изменения зависимостей выполнить install, audit в разумном объёме, lint, typecheck, tests и build.

## 18. Error handling

- Не проглатывать ошибки.
- Пустой `catch {}` запрещён без редкой и явно доказанной причины.
- Ошибки классифицировать по типу и обрабатывать на правильном уровне.
- Пользователю показывать понятное безопасное сообщение и возможное следующее действие.
- Технические детали, stack trace, внутренние идентификаторы и секреты не должны утекать в UI.
- Не использовать один универсальный fallback для всех ошибок, если пользователь может восстановиться точнее.
- Логирование и observability не должны дублировать одну ошибку на каждом слое.

## 19. Тестирование

- Добавлять тесты для критической бизнес-логики.
- Не писать тесты только ради coverage.
- Особенно тестировать calculations, parsing, validation, auth, permissions, API transformations, blockchain logic и critical user flows.
- Исправление бага по возможности сопровождается regression test, падающим до исправления.
- Для API проверять авторизацию, валидацию, ошибки, timeout и invalid response.
- Для UI проверять keyboard navigation, focus, адаптивность и обязательные состояния.
- Для критических пользовательских потоков использовать E2E-тесты.
- Перед завершением выполнять применимые format/check, lint, typecheck, tests и build.
- Не утверждать, что функциональность работает, если она фактически не проверена.
- Отчёт о проверке использовать в статусах PASS, FAIL, PARTIAL или NOT TESTED.
- Build, lint и typecheck не заменяют browser, integration и production QA.

## 20. Документация

README должен содержать:

- требования;
- установку;
- запуск;
- environment variables;
- dev workflow;
- build;
- testing.

- Документацию обновлять вместе с изменением поведения, контрактов, конфигурации и workflow.
- Не документировать очевидный код.
- Документировать архитектурные решения, ограничения и нестандартное поведение.
- Новые environment variables описывать без реальных секретов.
- `ARCHITECTURE.md` должен отражать фактическую, а не желаемую архитектуру; запланированные решения маркировать отдельно.
- `TODO.md` должен содержать актуальные Critical, High, Medium и Low задачи с краткой причиной.

## 21. Git

Рабочая ветка по умолчанию — `dev`.

Все изменения, коммиты и push выполняются исключительно в `dev`.

Без прямой команды пользователя в текущем диалоге, явно содержащей `main`, запрещены:

- commit в `main`;
- push в `main`;
- merge в `main`;
- rebase `main`;
- force push в `main`.

Фразы `можешь заканчивать`, `заливай`, `готово`, `пушь` и аналогичные не являются разрешением работать с `main`, если пользователь явно не написал `main`.

Перед каждым commit:

1. Проверить текущую ветку командой `git branch --show-current`.
2. Убедиться, что активна `dev`.
3. Проверить `git status`, `git diff` и staged diff.
4. Проверить отсутствие секретов и посторонних изменений.
5. Выполнить lint.
6. Выполнить typecheck.
7. Выполнить tests.
8. Выполнить build, если это разумно для проекта.

- Commit должен быть атомарным и относиться к одной задаче.
- Использовать короткие информативные Conventional Commits: `feat: add collection discovery page`, `fix: handle wallet disconnect`, `refactor: simplify marketplace filters`.
- Запрещены бессмысленные сообщения: `update`, `fixes`, `changes`, `final`, `test`.
- Не делать force push без прямого разрешения пользователя.
- Не выполнять merge, rebase, cherry-pick, удаление веток и изменение истории без прямого указания.
- Не обходить branch protection, hooks, CI и обязательные проверки.
- Не добавлять в commit чужие или несвязанные изменения.
- Не использовать destructive Git-команды для удаления пользовательской работы.
- Если Git не инициализирован, remote не настроен или `dev` отсутствует, сообщить об этом до commit или push.
- Запрос изменить файлы не является автоматическим разрешением на commit или push.

## 22. Финальная проверка

Перед завершением задачи убедиться:

1. Изменены только файлы в области задачи.
2. Пользовательские изменения сохранены.
3. Нет секретов, debug-кода, TODO, FIXME, лишних комментариев и мёртвого кода.
